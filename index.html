✳ AN HONEST PROJECT STORY

The hackathon
we didn't win.

And why I'm still glad we built Dishari.

“We didn't make the next round. I still want to remember what we built—and every mistake that taught us how.”
NOVEMBER 2026 · DISHARI

We wanted to help service-centre operators turn a messy packet of Aadhaar, bank passbook and Khatian documents into a reviewable case. So we built a three-step operator flow, multilingual UI, FastAPI integration, preliminary document checks and a synthetic demo that could keep the presentation going even when the network couldn't.

There were Docker Buildx errors, npm failures, ports to align, API paths to reconcile, and more last-minute debugging than anyone ordered. Our team didn't advance. That part matters. So does the fact that we shipped.

What workedHuman approval, three languages, offline demonstration, end-to-end thinking.
What changed meI now want to preserve every technical and nontechnical failure as a reusable postmortem—not bury it after the deadline.

✳ CHAPTER 03 / THE THINGS THAT BROKE

Debugging is just
curiosity under pressure.

Field notes from things that really
made me open another terminal.
01“npm error Exit handler never called!”Dishari · Docker build+

The build failed during npm ci. Rather than pretend the message revealed the cause, I investigated the npm logs, runtime resources, registry/network access and reproducible image setup. That message alone did not establish the root cause; we documented what to check rather than pretending we knew.

Lesson: logs first. Assumptions second.
02Buildx missing. Then permission denied.Dishari · Amazon Linux EC2+

Docker Compose required Buildx 0.17+; another attempt failed because the installed plugin couldn't execute. Version alignment, correct architecture, file permissions and a plain docker build/run fallback became part of the playbook.

Lesson: a deployment tool is itself a dependency.
03“Why can't Nginx find my backend?”MoodBuds · container networking+

Host ports, container ports and Docker DNS names don't mean the same thing. I learned to trace requests from inside the caller container, put services on a shared network, and preserve the intended API path at the reverse proxy.

Lesson: always draw the request path.
04Encrypted Linux wouldn't boot.Arch Linux · LUKS recovery+

A storage change left my encrypted-root setup in trouble. Recovery used a verified LUKS header backup. Afterwards I archived important data and verified backup integrity rather than treating “it runs on my machine” as a recovery strategy.

Lesson: reliability begins before disaster.

✳ WHAT THE WORK TAUGHT ME

I don’t collect titles.
I collect questions.

The same pattern keeps showing up, whatever I'm building.

01 / BLUE

Who owns the truth?

In PixelMania, the server owns movement and combat. In Dishari, humans approve and rules—not a language model—evaluate eligibility. The details change. The trust boundary doesn't.

02 / RED

Where does the request go?

Browser → proxy → container → API → worker. Tracing that journey taught me more than memorizing cloud service names ever did.

03 / YELLOW

What happens when it breaks?

Docker builds, a broken encrypted boot, an unreachable backend, a hackathon deadline. I want the logs, root-cause hypotheses, recovery path, and a prevention test—not a heroic story.

04 / GREEN

Can it really get better?

TenseBots is an unfinished experiment in autonomous DevSecOps. The interesting proof isn't that an agent can talk. It's whether we can measure safer, smarter behavior after verified learning.

Proof over adjectives. I separate prototypes from deployed work and future ideas from validated results. Read my engineering archive ↗
